Devin Desktop + CLI Walkthrough: Ship a “Favorites” Tray in Open MCT

  • Audience: Engineers evaluating Devin Desktop + CLI (especially those working in JavaScript/Vue codebases)
  • Repo: nasa/openmct (master branch)
  • Docs home: docs.devin.ai/desktop

🎯 Goal. In this walkthrough you’ll ship a “Favorites” tray to NASA’s Open MCT — a right-click Add to Favorites action on any object in the tree and a new header tray that lists what you pinned — working primarily in Devin Desktop, with a Devin CLI tour at the end. You’ll understand the codebase with DeepWiki + Codemaps, plan the feature with Cascade’s Ask and Plan modes, build it the team’s way with AGENTS.md + Skills (with Tab accelerating your manual edits), and verify it in a live browser. By the end you have a working, on-screen feature — and the same skills apply to any repo you bring.

🧵 The throughline — follow the Favorites feature end to end. Every part below is in service of one feature: understand → plan → build → verify. Keep coming back to it so each capability feels motivated, not like a feature checklist.

Part 0 — Set up

0.1 — Clone with Devin Desktop

  1. Open Devin Desktop.
  2. From the launcher, choose Clone repository (or open the Command Palette — the “search” bar at the top center, Cmd+Shift+P on macOS, Ctrl+Shift+P on Windows/Linux — and run Git: Clone). You can also click the Explorer icon in the top left and then click Clone Repository to do the same thing.
  3. Paste the repo URL: https://github.com/nasa/openmct, pick a local folder, and open the cloned workspace when prompted.
  4. When Devin Desktop asks whether to trust the workspace, accept — the AI features (DeepWiki hovers, Codemaps, Cascade) need workspace access.

0.2 — Alternatively, clone from the terminal

git clone https://github.com/nasa/openmct.git
cd openmct

0.3 — Install the Devin CLI

The Devin CLI is bundled with Devin Desktop, or installable standalone:

  • FedRAMP users: https://windsurf.fedstart.com/install/cli
  • Non-FedRAMP users (see the CLI quickstart for all platforms):
    • From Devin Desktop: open the Command Palette and run Install Devin CLI (an admin must have enabled Show “Install Devin CLI” in the Devin Desktop Command Palette in team settings).
    • macOS / Linux / WSL: curl -fsSL https://cli.devin.ai/install.sh | bash
    • Homebrew: brew install --cask devin-cli
    • Windows (PowerShell only): irm https://static.devin.ai/cli/setup.ps1 | iex

Then verify and log in:

cd path/to/openmct   # e.g. cd ~/repos/openmct, wherever you cloned it
devin        # inside the openmct directory
/login       # opens a browser to authenticate

If you cloned with Devin Desktop, you can instead open the built-in terminal (Terminal → New Terminal, or Ctrl+`) — it opens already scoped to the repo folder.

0.4 — Install dependencies and start the dev server

Open MCT needs Node.js ≥ 24.14.1 (the repo pins the exact version in .nvmrc — nvm install picks it up automatically).

The easy way: have Devin Desktop do it. Open the Cascade panel and prompt:

Prompt
Set up this repo and start the dev server. Tell me the URL to open and flag anything missing on my machine.

Note: you can probably just ask Cascade some variation of “set up this repo” and let it make the smart choices, though you can be as prescriptive as you’d like — often a good idea if the setup is tricky and you know it well.

Devin will run nvm install, npm install, and npm start (approving the shell commands as they come up), surface any missing prerequisites, and report the URL.

Or run it yourself:

nvm install
npm install
npm start

The dev server comes up at http://localhost:8080/ — open it and confirm the Open MCT shell loads with the object tree on the left. This is your “start state” and your Part 5 verification path.

0.5 — Agent-config files you’ll create during this walkthrough

This repo doesn’t ship any agent configuration yet — you’ll create it as you go, exactly as you would on your own repo:

  • AGENTS.md (repo root) — a “README for agents”: project overview, exact build/lint/test commands, code conventions, and boundaries. You’ll write it in Part 3.1, including how to think about what goes in it.
  • .devin/skills/mct-plugin-pre-pr-check/SKILL.md — a /mct-plugin-pre-pr-check skill that runs the quality gate plus a diff self-review. You’ll write it in Part 4.1.

Part 1 — Understand the codebase (Desktop: DeepWiki + Codemaps + Tab)

📖 Open MCT is NASA’s open-source mission control framework — a JavaScript/Vue 3 web application built with webpack, used for spacecraft telemetry visualization. Nearly every feature is a plugin: a function returning an install(openmct) callback that registers types, views, actions, and indicators through the openmct API (openmct.install(MyPlugin()) — see src/MCT.js).

1.1 — Codemaps: see the flow

Use Codemaps to visualize how the pieces fit together — the order in which code executes and how components relate. DeepWiki explains symbols; Codemaps explain flow.

  1. Open a sample file: in the Command Palette, search for the file plugin.js in the notebook plugin (src/plugins/notebook/plugin.js).

  2. Open the Codemaps panel from the Activity Bar (left side).

  3. Create a new Codemap with a custom prompt, for example:

    Prompt
    Map how the Notebook feature works, from plugin registration to how entries are persisted.

    Note: there are two modes, Fast (use Fast for this example) and Smart (slower and better).

  4. The Codemap agent will explore the repo and generate a hierarchical, clickable view. Click any node to jump straight to that file and function — walk from NotebookPlugin → NotebookViewProvider → NotebookComponent.vue.

  5. You can send the Codemap into a Cascade conversation so the agent reasons over the same map you’re looking at (three dots on the top right of the Codemap, then click Send to Cascade).

  6. Check out the other Codemap features, including diagram view and chat. Sharing is disabled for the ZDR FedRAMP implementation.

This is where a Favorites tray will plug in.

1.2 — DeepWiki: understand symbols in place

Open a template file, e.g.:

src/plugins/notebook/NotebookViewProvider.js
  • Hover a symbol like openmct.objectViews.addProvider, canView(domainObject), or the mount(...) helper and press Cmd+Shift+Click to open DeepWiki’s detailed explanation — unlike classic hover cards that show only type info, DeepWiki explains what the symbol does and why.
  • From the DeepWiki panel, click ⋮ → Add to Devin Cascade to send the explanation into your chat as a reference.
  • Try asking a question in Ask mode, for example: “How do plugins add context-menu actions and header indicators?”

1.3 — Tab: fluent manual navigation and edits

While you’re reading code, try Devin Desktop Tab — the in-house, flow-aware suggestion engine you’ll lean on for any manual edits in Part 3. Tab is built into the editor — there’s no panel to open. Just start typing in any file and suggestions appear automatically; press tab to accept, esc to dismiss. Learn about Autocomplete, Supercomplete, Tab to Jump, and Tab to Import in the docs.

Tab mode — in the already-open src/plugins/notebook/plugin.js:

  1. Inline suggestion / Supercomplete (diff-style suggestion windows around your cursor proposing both deletions and additions, before and after the cursor position). This file contains two near-identical functions: NotebookPlugin (~line 95) and RestrictedNotebookPlugin (~line 121) — same shape, different constants. Click after the closing brace of RestrictedNotebookPlugin (~line 144), press Enter twice, and type function AnnotatedNotebookPlugin( — Tab reads the repeating pattern and proposes a whole matching function body (installer, NotebookType, addProvider). Press tab to accept, or esc to dismiss.

When you’re done, undo everything with Cmd+Z / Ctrl+Z — these edits were just for the tour.

Good to know:

  • Context awareness — suggestions draw on your code, terminal activity, Cascade chat history, recent actions, and (opt-in via advanced Settings) your clipboard.
  • Shortcuts: accept = tab; cancel = esc; accept word-by-word = ⌘+→ (VS Code). Suggestions disappear if you keep typing or navigating.
  • Settings: open Settings (Cmd+, / Ctrl+,) to switch between Autocomplete and Supercomplete, toggle Tab to Jump / Tab to Import individually, and opt in to clipboard context. If nothing appears while trying the steps above: type another character or two (suggestions vanish when you pause or navigate away), and confirm Supercomplete, Tab to Jump, and Tab to Import are enabled.

✅ Checkpoint: you can point at the plugin installer pattern, the view-provider template, and the persistence pattern the feature will reuse — and you’ve accepted a Tab suggestion in each mode.

Part 3 — Build it the team’s way (Desktop)

3.1 — Create AGENTS.md

What it is: AGENTS.md is a “README for agents” that lives at the repo root — always-on context loaded into every session (it’s also discovered in subdirectories and parent dirs up to the git root). It’s how a team encodes its conventions once so every agent, on every machine, builds the same way.

How to think about writing one — for this repo or any repo, capture the four things an experienced teammate would tell a new hire:

  1. Project overview — what the codebase is and how it’s organized, in a few lines.
  2. Commands — the exact dev, lint, and test commands, including the fast paths (npm run lint:js is faster than the full npm run lint; unit tests are separate from Playwright e2e).
  3. Code conventions — the patterns the repo actually follows: how plugins are structured, which APIs to use, required boilerplate (like Open MCT’s license header).
  4. Boundaries — what the agent must not touch.

A fast way to draft it: ask Cascade in Ask mode — “Draft an AGENTS.md for this repo: overview, commands, code conventions, and boundaries.” Then review and tighten it. For this walkthrough, create AGENTS.md at the repo root with:

# AGENTS.md

## Project overview
Open MCT: NASA's open-source mission control framework. A JavaScript /
Vue 3 web application built with webpack. Features are plugins under
src/plugins/, each an installer function registered via openmct.install().
Core APIs (actions, indicators, views, types, router) live under src/api/
and src/ui/.

## Commands
- Node: >= 24.14.1 (pinned in .nvmrc — use `nvm install`)
- Install deps: `npm install`
- Dev server: `npm start` (webpack-dev-server at http://localhost:8080/)
- Lint: `npm run lint` (or `npm run lint:js` / `npm run lint:vue`; fix with
  `npm run lint:fix`)
- Unit tests: `npm test` (Karma/Jasmine; specs are *Spec.js next to source)
- E2E tests: `npm run test:e2e:local` (Playwright, under e2e/)
- Build: `npm run build`

## Code conventions
- ES modules with explicit .js extensions in import paths
- Source files start with the Open MCT Apache 2.0 license header — copy it
  from a neighboring file verbatim (Vue files use the HTML-comment form)
- New features are plugins: src/plugins/<feature>/plugin.js exports a
  function returning an install(openmct) callback; register built-ins in
  src/plugins/plugins.js
- Context-menu items are actions: classes with appliesTo(objectPath) and
  invoke(objectPath), registered via openmct.actions.register (see
  src/plugins/remove/RemoveAction.js)
- Header trays are indicators: openmct.indicators.add({ key, vueComponent,
  priority }) (see src/plugins/notificationIndicator/plugin.js)
- UI is Vue 3 single-file components; mount with utils/mount like
  NotebookViewProvider does
- Navigate with openmct.router.navigate('#/browse/…') — never manipulate
  window.location directly
- Unit specs live next to the code as pluginSpec.js / *Spec.js

## Boundaries
- Don't modify core APIs under src/api/ or src/ui/ for a feature that can
  live in a plugin
- Don't touch the webpack configs (.webpack/) or package.json for a
  feature under src/plugins/
- Never edit vendored or generated code (dist/, node_modules/)

Then ask in Cascade:

Prompt
What conventions should you follow when adding the favorites plugin and its indicator?

Devin reflects back the repo’s rules: license header, installer-function plugin, action API, indicator API, Vue SFC + mount, router.navigate. Your plan from Part 2 now has guardrails.

Part 4 — Extend the agent (Skills)

4.1 — Create a Skill and gate the work with it

What it is: a Skill is a reusable procedure committed to the repo under .devin/skills/<name>/SKILL.md. See the creating Skills guide for the file format. The directory name becomes the skill name and its slash command, so everyone on the team runs the same gate the same way.

How to think about writing one: capture a procedure you’d otherwise repeat in prompts — ordered steps, exact commands, and the checks that matter for this repo. A pre-PR quality gate is the classic first skill.

Create .devin/skills/mct-plugin-pre-pr-check/SKILL.md:

---
name: mct-plugin-pre-pr-check
description: Run the full pre-PR quality gate — lint, unit tests, and a
  self-review of the diff. Use before creating or updating any pull request.
---

# Pre-PR Quality Gate

Follow these steps in order. Do not skip steps.

1. Run `npm run lint` and fix any errors (use `npm run lint:fix` for
   auto-fixable issues).
2. Run `npm test` and ensure the unit tests pass.
3. Review your own diff with `git diff` and check:
   - Every new file carries the Open MCT Apache 2.0 license header
   - No debug statements (console.log, debugger) left behind
   - No commented-out code
   - Import paths include explicit .js extensions
   - No edits outside src/plugins/ for this feature (plus the one-line
     registrations in src/plugins/plugins.js)
   - No changes to package.json or the .webpack/ configs
4. Summarize what was checked and the results before proceeding.

Then run it:

/mct-plugin-pre-pr-check

Devin runs lint → tests → a diff self-review.

4.2 — Add a release-notes Skill

Create a second skill at .devin/skills/release-notes/SKILL.md:

---
name: release-notes

Read `git log` since the last tag, summarize the user-visible changes, and draft:

Invoke it with:

/release-notes

Part 5 — Verify it actually works (live browser)

Open MCT is a web app, so verification is a dev-server launch + click-through. First ask Cascade:

Prompt
How do I verify the Favorites feature in the browser? Give me the click path.

Then, live on screen (at http://localhost:8080/ — webpack hot-reloads your changes, so the running app already has them):

  1. Wait for the Open MCT shell to load, with the object tree on the left.
  2. Right-click an object in the tree (e.g. one under My Items) → Add to Favorites.
  3. Click the new Favorites tray in the header — the object is listed; add one more.
  4. Click a listed favorite — Open MCT navigates to that object.
  5. Remove one with Remove from Favorites.
  6. Reload the page — the favorites survive (localStorage).

5.1 — Bonus: let Cascade debug from the terminal

Cascade doesn’t just see your files — it sees your terminal output too. To prove it, break something on purpose: open src/plugins/favorites/plugin.js and typo one of the import paths (e.g. change ./favoritesStore.js to ./favoritesStor.js). Save, and watch the npm start terminal fill with a webpack Module not found error. Then just ask Cascade:

Prompt
The dev server is failing — fix it.

Cascade reads the webpack error from the terminal, traces it to the broken import, and fixes the path — no copy-pasting stack traces. This is the everyday loop: run it, let the agent read what the terminal says, and fix from the actual error.

✅ Checkpoint: the feature works end-to-end in a live Open MCT — and you’ve seen Cascade debug from real terminal output.

6.5 — Two more CLI tricks

Run a raw shell command from the interactive session. At the REPL prompt, prefix a command with ! to enter bash mode and run it directly — for example, !npm run lint. See the CLI keyboard shortcuts for the ! bash-mode entry and exit behavior.

!npm run lint

Use non-interactive print mode in a pipe. The CLI’s --print / -p flag prints the response and exits, so you can pass a diff on standard input and ask for a commit message:

git diff | devin -p "write a commit message for this change"

6.6 — Connect an MCP server

MCPs (Model Context Protocol servers) are how you give the agent scoped, real tools — browsers, docs, databases, internal systems. Because Open MCT is a web app, the perfect MCP for this walkthrough is Playwright, which gives the agent a real browser (MCP configuration docs):

devin mcp add playwright npx @playwright/mcp@latest

You can also give Devin the URL, or just tell Devin to install the Playwright MCP.

Now have the agent verify its own feature:

Use the playwright MCP to open http://localhost:8080/, add an object to Favorites from the tree's right-click menu, and confirm it shows up in the Favorites tray. Reload and confirm it's still there.

Devin drives a real browser through the same click path you did by hand in Part 5 — the agent verifying its own work. (Another no-auth option: devin mcp add deepwiki https://mcp.deepwiki.com/mcp serves AI-generated docs for public GitHub repos, including nasa/openmct.)

Scoping — where MCP config lives:

ScopeFileShared?
local (default).devin/config.local.jsonNo — gitignored; put tokens here
project.devin/config.jsonYes — committed, shared with the team
user~/.config/devin/config.jsonNo — all your projects

💡 Note — two agent harnesses, two MCP configs. Cascade (the agent panel in Devin Desktop) and Devin Local (the agent behind the Devin CLI) are different harnesses with separate MCP configurations — an MCP server added to one will not appear in the other.

  • Cascade (Desktop): configured from the MCP panel in Cascade (or its Plugins page); the raw config file is ~/.codeium/windsurf/mcp_config.json.
  • Devin Local (CLI): configured with devin mcp add (or by editing the files directly); config lives in the scoped files above — .devin/config.local.json (local, gitignored), .devin/config.json (project, committed), or ~/.config/devin/config.json (user; %APPDATA%\devin\config.json on Windows).

If you want the Playwright MCP available in both, add it in both places.

6.7 — Manually add an MCP in Devin Desktop (no marketplace)

If the server you want isn’t in the MCP Marketplace, add it by editing Cascade’s raw config file directly (Cascade MCP docs):

  1. Open the MCP panel. Click the MCPs icon in the top-right menu of the Cascade panel, or go to Devin Settings → Cascade → MCP Servers. (Enterprise users: an admin must enable MCP access first.)
  2. Open the raw config. From that panel, open mcp_config.json — or edit the file directly at ~/.codeium/windsurf/mcp_config.json (create it if it doesn’t exist).
  3. Add your server under the mcpServers key. For a local (stdio) server like Playwright:
    {
  "mcpServers": {
    "playwright": {
      "command": "npx",
      "args": ["-y", "@playwright/mcp@latest"]
    }
  }
}

    For a remote HTTP server, use serverUrl instead of command:

    {
  "mcpServers": {
    "deepwiki": {
      "serverUrl": "https://mcp.deepwiki.com/mcp"
    }
  }
}

    Don’t hardcode secrets — the config supports ${env:VAR_NAME} and ${file:/path/to/file} interpolation in command, args, env, serverUrl, url, and headers.

  4. Save the file, then go back to the MCP panel and refresh — the new server appears alongside the marketplace ones.
  5. Enable its tools. Click the server in the MCP panel and toggle the tools you want (Cascade has a limit of 100 total enabled tools at a time).
  6. Verify. Ask Cascade something that requires the new server (e.g. “Use the playwright MCP to open http://localhost:8080/.”) and watch it call the tool.

6.8 — Hooks: run your own logic on agent events

Hooks let the CLI run your own commands when the agent does things — before a tool runs, after it finishes, when a session starts, and so on (full event list). Simplest useful example: log every shell command the agent runs. Step by step:

  1. Create the hooks file at .devin/hooks.v1.json in the repo root:
    {
  "PostToolUse": [
    {
      "matcher": "exec",
      "hooks": [
        {
          "type": "command",
          "command": "sh -c 'cat >> ~/.devin-command-log'"
        }
      ]
    }
  ]
}

    Reading it: after (PostToolUse) every shell command (matcher: "exec"), run this command — the event arrives as JSON on stdin, and here it’s appended to a log file.

  2. Start a fresh session in the repo — run devin (hooks are loaded at session start).
  3. Make the agent run something, e.g.:
    Prompt
    Run the linter and tell me if it passes.
  4. Check the log:
    cat ~/.devin-command-log

    Every shell command the agent executed is there, as JSON.

💡 What people actually use hooks for:

  • Guardrails — block dangerous commands (rm -rf, git push --force, prod database URLs) with a PreToolUse hook that exits non-zero
  • Audit & compliance — log every command, edit, or permission decision to a file or SIEM (PostToolUse)
  • Auto-format on save — run prettier/eslint --fix on any file the agent edits (PostToolUse on edit)
  • Protected paths — require confirmation (or refuse) when the agent touches lockfiles, CI config, or generated files
  • Notifications — ping Slack or the desktop when a long session finishes or wants permission (Stop, PermissionRequest)
  • Inject context — add reminders when specific tools fire, e.g. “staging DB only” whenever a psql command runs (UserPromptSubmit/PreToolUse)
  • Command rewriting — transparently route commands through a wrapper (e.g. prepend a sandbox or proxy) via updatedInput

That’s the whole loop: a JSON file, a matcher, a command. The same mechanism scales up — a PreToolUse hook can block a tool call by exiting non-zero (e.g. refuse any command containing rm -rf), inject context, or rewrite commands before they run. Hooks are a Devin CLI feature; in Desktop, use AGENTS.md and Skills for guidance instead.
